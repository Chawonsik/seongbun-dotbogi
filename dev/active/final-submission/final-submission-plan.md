# 최종 제출 준비 (마감 2026-10-15 목 15:00)

## Context
최종 프로젝트 심사 안내(2026-10-08)에 따라 10/15 15:00까지 팀원이 각자 네 가지를 낸다: 공개 URL(리포트 페이지, 대시보드, 앱 중 하나), GitHub 저장소 README, 발표 슬라이드 링크, 제출 폼 답. 2차 광고는 10/16 18:00에 끝나므로 제출 시점의 2차는 중간값이다.

심사 100점: 문제 정의 15, 데이터 근거 30(주장마다 차트나 수치 10, 데이터 설명 5, 전처리 기록 5, 검증 방법 5, 한계 5), 해결 방법 15, 완성도 10, 전달력 10, 심사위원 20. AI 사용을 밝히지 않으면 제출을 받지 않는다. README는 정해진 틀(한 줄 요약과 공개 URL, 1~8절)을 따르고 절마다 기준표 항목이 채워진다.

지금 저장소 README는 폴더, 운영 규칙, 브랜치 방식만 있어서 심사 틀과 맞지 않는다. 공개 URL로 낼 결과물은 없다.

정해진 것(2026-10-11 차원식)
- 결과물 형태: 미정, 10/12에 정함
- 슬라이드: 나중에 정함
- 성공 기준: "미리 정했고 바꿨다"로 사실대로 쓴다

그래서 이번 계획은 결과물 형태와 상관없이 지금 할 수 있는 것(README, 수치와 차트 재료, 사람이 채울 칸 정리)부터 한다.

## 단계

### A. README를 심사 틀로 다시 쓰기 (지금)
파일: `README.md`. 지금 README의 브랜치 작업 방식과 배포 설명은 `docs/workflow.md`로 옮기고 6절에서 링크한다(내용은 그대로 옮김).

| 절 | 넣을 것 | 출처 |
|---|---|---|
| 머리 | 한 줄 요약(누가, 어떤 상황, 무엇이 문제, 무엇을 내놓았나), 공개 URL(형태가 정해지면 채움) | 메모리의 확정 제목과 설명, 결정 로그 1절 |
| 1. 문제 정의 | 대상과 문제 한 문장. 비즈니스 임팩트는 우리가 잰 수치로만(클릭당 비용, 랜딩 조회당 비용, 같은 예산에서의 클릭 수). 성공 기준(10/1에 정한 것과 10/7에 바꾼 것). Focus 지표 CTR(링크 클릭률), 선행지표 후보는 노출 비중과 노출 단가 | 결정 로그 3~5절, 캠페인 시작 기록 |
| 2. 데이터 | 출처(Meta 광고 관리자 수치, Amplitude 이벤트, 화해 리뷰 약 110개의 집계), 기간, 행 수, 주요 열. 전처리: 무엇을 왜 걸렀고 전후 수가 몇인지 | `docs/taxonomy/events.csv`, 조회로 전후 수를 구함 |
| 3. 분석과 검증 | 주장마다 수치(분자, 분모, 비교 대상)와 차트. 사실과 해석을 나눠 씀. 검증 방법(광고 세트 2개의 균등 분배, 링크 클릭과 랜딩 도착 대조, 함께 나간 날만 비교)과 고른 이유 | 캠페인 시작 기록의 1차 최종 결과, 2차 중간 기록 |
| 4. 해결책 | 어느 분석에서 나왔나(1차 노출 쏠림 → 세트 분리, 랜딩 이탈 → 3차 제안). 누가 무엇을 하면 어느 지표가 움직이나. 사용자 확인 | context의 3차 제안 재료. 반응은 사람이 받아 옴 |
| 5. 한계 | 표본 규모, 연휴, 가상 제품, 릴스와 아이폰에 쏠린 노출, 구역 기록의 측정 기간, 관심이지 구매가 아님 | context "분석 결과를 쓸 때" |
| 6. 실행법과 폴더 | 폴더 구조, 로컬에서 여는 법, 택소노미 검사 실행법, `docs/workflow.md` 링크 | 지금 README, `landing/README.md` |
| 7. AI 사용 공개 | 쓴 도구와 쓴 곳, 핵심 프롬프트, 사람이 검증하거나 고친 곳 | 이 대화의 기록. 다른 대화와 권지원 쪽은 사람이 채움 |
| 8. 나의 역할 | 팀원별 맡은 부분과 내린 결정 | 커밋 기록과 문서로 초안, 본인이 확정 |

쓰는 규칙
- 예상 클릭률, 표본 오차, 운으로 벌어지는 차이는 쓰지 않는다. 0.7%p는 "처음 정했다가 뺀 기준"으로 경위만 적는다.
- 관찰과 해석을 나눈다. "사용감 그림이 이겼다", "랜딩을 고쳐서 나아졌다"는 쓰지 않는다.
- 2차는 중간값이라고 밝히고 조회 시각을 적는다.
- 기기 단위 정보는 넣지 않고 집계만 쓴다.
- 분석 환경은 확정 문구를 그대로 쓴다: "Meta 광고와 Amplitude를 AI에 연결해 조회, 분석, 기록을 한 자리에서 하는 분석 환경".

조회해서 채울 수치(README 2절)
- Amplitude 이벤트 수와 기기 수: 1차 기간과 2차 기간, 걸러내기 전과 후(is_test, 봇, 우리나 메타가 연 방문, 기간 밖)
- Meta: 광고별 일자별 행 수

사람이 채울 칸(초안에 표시해 둠)
- 4절의 읽은 사람 반응(누가 읽었고 뭐라고 했는지)
- 7절에서 이 대화 밖의 AI 사용(광고 이미지, 권지원 쪽 작업 등)
- 8절의 역할과 내린 결정

### B. 차트 재료 (결과물 형태와 무관하게 쓰임)
README와 결과물에 같이 쓸 차트를 정적 SVG로 만든다. dataviz 스킬을 따른다.
- 1차 일자별 노출(원료 대 사용감)
- 노출 비중: 1차(7% 대 93%) 대 2차(약 50% 대 50%)
- 2차 CTR A 대 B(누적과 일자별)
- 랜딩 퍼널: 도착, 버튼이 화면에 들어옴, 버튼 클릭 (1차와 2차)

수치는 `docs/report/data.json` 한 곳에 두고 `scripts/make_report_charts.py`가 SVG를 `docs/report/img/`에 만든다. 10/15 오전에 2차 수치만 바꿔 다시 뽑는다. 스크립트는 기존 `scripts/test_check_taxonomy.py`와 같은 방식(unittest)으로 간단한 테스트를 둔다.

### C. 공개 URL 결과물 (10/12에 형태가 정해진 뒤)
형태가 정해지면 별도로 계획한다. 리포트 페이지라면 `landing/report.html`과 `vercel.json` rewrites 한 줄(`/report`), 계측은 넣지 않음(택소노미 변경 없음), 첫 화면에 문제, 핵심 결과, 해결책.

### D. 슬라이드 (나중에)
장별 내용과 넣을 수치, 차트를 정리해 드린다. 형태는 그때 정한다.

## 검증

- `python3 scripts/check_taxonomy.py`가 그대로 통과하는지(랜딩을 건드리지 않았으므로 변화가 없어야 함).
